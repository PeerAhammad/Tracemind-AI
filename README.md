# TraceMind AI
**Observe. Diagnose. Repair. Verify.**

AI-agent debugging and reliability platform: ingest execution traces, detect failures with deterministic rules,
explain them with trace evidence, propose fixes, replay a controlled task, and measure the improvement.

> Status: backend complete (Stage 5). Frontend in progress. Trace upload/validation and three rule-based detectors (repeated calls without progress,
> explicit tool errors, unsupported completion claims) are implemented. A deterministic task runner with mock tools,
> SQLite storage, correction proposals, approval-gated replay and before/after comparison are implemented.
> A 28-scenario labelled benchmark with precision/recall is implemented. The frontend is not implemented yet.

## API (current)
- `GET /api/health`
- `POST /api/traces` (multipart file upload, JSON, max `MAX_UPLOAD_BYTES`)
- `GET /api/traces/{id}`
- `POST /api/traces/{id}/analyze` runs all detectors, returns findings with evidence event ids
- `GET /api/traces/{id}/findings` last analysis result
- `GET /api/tasks` available controlled tasks
- `POST /api/tasks/run` body `{task_id, configuration?}` runs a task, stores the run and its trace
- `POST /api/tasks/evaluate` body `{configuration}` runs all tasks under default vs candidate config (fixes and regressions)
- `GET /api/runs/{id}` run with events, outcome, tool-call count, simulated duration
- `POST /api/runs/{id}/analyze` detectors on a run's trace
- `GET /api/runs/{id}/corrections` proposed config changes (nothing is applied)
- `POST /api/runs/{id}/replay` body `{approved: true, approved_changes}` reruns the same task with the approved config
- `GET /api/runs/{id}/comparison` baseline vs replay (works with either run id)
- `GET /api/benchmark` live benchmark metrics (precision, recall, TP/FP/TN/FN, held-out split, runner sweep)
- `GET /api/benchmark/saved` saved results file
- `GET /api/benchmark/scenarios`, `GET /api/benchmark/scenarios/{id}`, `POST /api/benchmark/scenarios/{id}/load`

## Detectors (Stage 2)
All detectors are deterministic and need no LLM. They are heuristics over recorded traces, not general failure detection.
- **repeated_call_no_progress**: >= 3 back-to-back calls with equivalent input AND equivalent result. Not flagged: changed result (retry that recovered, polling progress), changed input, interleaved calls, allow-listed tools.
- **explicit_tool_error**: any call with `error_details`. LOW if a later call to the same tool succeeded, HIGH otherwise.
- **unsupported_completion_claim**: success claimed (status `completed`, or non-negated success wording in the final answer) while the last tool call failed, or a step ran on empty input after an empty result.

No benchmark metrics exist yet, so no accuracy claims are made.

## Controlled runner (Stage 3)
The runner is a deterministic, policy-driven workflow, not an LLM agent. Its behaviour depends only on the task
(`benchmarks/tasks/*.json`) and `RunConfig` (`max_retries`, `reformulate_on_empty`, `require_retrieval_before_summary`),
so replaying with a changed config is a real behavioural change. Tools are in-process mocks; durations are simulated
and token usage is not available. `task_outcome` is ground truth: the agent reported completion AND the summary was built
from text containing the task's expected fact.

A finding is marked `fix_verified` only after a replay in which its failure category is gone and the task did not regress.
`fix_not_effective` is used otherwise. Only 3 tasks exist so far, so these numbers say nothing about general reliability.

## Benchmark (Stage 4)

**Method.** 28 hand-labelled scenarios in `benchmarks/scenarios/` (generated by `benchmarks/generate_scenarios.py`): 18 `dev` scenarios used while designing the rules and 10 `heldout` scenarios written after the detector code was frozen. Each scenario has a recorded trace, ground-truth failure categories with minimal evidence events, the expected task outcome, expected detector behaviour and the expected corrective change. Unit of analysis: one (scenario, category) cell (28 scenarios x 6 categories = 168 cells), labelled present/absent by hand. Precision = TP/(TP+FP), recall = TP/(TP+FN), FPR = FP/(FP+TN); `n/a` means undefined (zero denominator).

Reproduce: `cd backend && python -m app.evaluation.run_benchmark` (add `--write` to refresh the saved results). Live: `GET /api/benchmark`. Saved: `GET /api/benchmark/saved`.

**Results (saved, reproducible; a test fails if they drift from the live computation).**

| split | scenarios | TP | FP | TN | FN | precision | recall | FPR |
|---|---|---|---|---|---|---|---|---|
| dev | 18 | 15 | 0 | 93 | 0 | 1.000 | 1.000 | 0.000 |
| held-out | 10 | 6 | 1 | 51 | 2 | 0.857 | 0.750 | 0.019 |
| overall | 28 | 21 | 1 | 144 | 2 | 0.955 | 0.913 | 0.007 |

Evidence hit rate on true positives (labelled events covered by the finding's evidence): overall 1.000, held-out 1.000. Clean scenarios flagged: 1 of 10.

**The dev result is not evidence of generalization**: the rules were designed alongside those scenarios. The held-out row is the more honest number, and it is based on only 10 scenarios.

**Known misses and false alarms on the held-out set (not fixed, on purpose):**
- `H07`: False negative: alternating identical calls (A, B, A, B, ...) with unchanged results are a loop, but the repeated-call rule only looks at consecutive calls.
- `H08`: False negative: the tool failed inside its *output* (`status: failed`) with no `error_details`; the completion detector only checks `error_details` and empty data flow.
- `H09`: False positive: an empty optional argument after an empty search is legitimate here, but the empty-data-flow rule flags it.

**Controlled-runner effect of the full proposed fix** (`runner_sweep`, live runs of the 3 runnable tasks, simulated durations):
completion rate 0.667 -> 1.000, tool calls 9 -> 8, tasks fixed ['refund_empty_search'], tasks regressed [].

**Limitations**

- 28 hand-written scenarios: far too few to establish general reliability of the detectors.
- Ground truth, detectors and scenarios were all written by the same team; the held-out set was written after the detector code was frozen, but it is not independent or blind.
- Traces are synthetic and short; real agent traces are noisier.
- Missing-step, invalid-sequence and contradiction detectors only work when the trace configuration declares required_steps, sequence_rules or constraints.
- Corrective-change effects are measured only on the 3 runnable tasks (runner_sweep), not on every scenario.
- Durations in runner_sweep are simulated by deterministic mock tools; token usage is not measured.

Detectors implemented: repeated calls, explicit tool errors, unsupported completion claims, missing required steps, invalid action sequences, evidence/constraint contradictions. The last three read `required_steps`, `sequence_rules` and `constraints` from the trace's `initial_configuration`.
